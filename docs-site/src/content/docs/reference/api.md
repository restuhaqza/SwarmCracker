> The public HTTP API (v1) and the internal gRPC protocol between swarmd-firecracker and swarmcracker CLI / swarmctl.

---

## Overview

SwarmCracker has two machine surfaces:

| Surface | Audience | Contract |
|---------|----------|----------|
| **HTTP API v1** | operators, CI, external readers | `api/openapi.yaml` — see [Public HTTP API (v1)](#public-http-api-v1) |
| **gRPC control protocol** | the CLI and `swarmctl` against a cluster member | internal; versioned with `x-swarmcracker-version` (this page, below) |

The gRPC section is the *internal* protocol: it is not a supported integration
point and its messages may change with SwarmKit. The HTTP API is the public,
documented contract.

SwarmCracker uses **SwarmKit's gRPC API** via the `github.com/moby/swarmkit/v2/api` package, extended with a custom **API versioning protocol** (`pkg/apiversion`).

```
┌──────────────────┐       Unix Socket       ┌────────────────────────┐
│  swarmcracker    │ ───── gRPC (TLS) ────── │  swarmd-firecracker    │
│  swarmctl        │   /var/run/swarmkit/     │  (manager/worker)      │
│                  │       swarm.sock         │                        │
└────────┬─────────┘                          └───────────┬────────────┘
         │                                                 │
         │  X-SwarmCracker-Version: 1                       │
         │  (gRPC metadata interceptor)                     │
         └─────────────────────────────────────────────────┘
```

## Connection

### Control Socket

| Parameter | Value |
|-----------|-------|
| **Socket path** | `/var/run/swarmkit/swarm.sock` |
| **State directory** | `/var/lib/swarmkit` |
| **Transport** | Unix socket + TLS |
| **Certificates** | Auto-generated by SwarmKit CA |

### Connecting (Go)

```go
import (
    "github.com/moby/swarmkit/v2/api"
    "github.com/restuhaqza/swarmcracker/pkg/apiversion"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials"
)

// Load TLS certificates from state dir
tlsConfig := loadTLSConfig("/var/lib/swarmkit")

conn, err := grpc.Dial(
    "unix:///var/run/swarmkit/swarm.sock",
    grpc.WithTransportCredentials(credentials.NewTLS(tlsConfig)),
    apiversion.WithVersion(), // Injects X-SwarmCracker-Version metadata
)
client := api.NewControlClient(conn)
```

## API Versioning

SwarmCracker extends SwarmKit with a gRPC **unary client interceptor** that injects metadata into every outgoing RPC.

### Protocol

| Header | Value | Description |
|--------|-------|-------------|
| `x-swarmcracker-version` | `"1"` | Current API version |

### Client Side

```go
import (
    "github.com/restuhaqza/swarmcracker/pkg/apiversion"
    "google.golang.org/grpc"
)

conn, err := grpc.Dial(addr,
    grpc.WithTransportCredentials(creds),
    apiversion.WithVersion(), // Injects X-SwarmCracker-Version metadata
)
```

### Server Side

The package is client-only. It exports `Current`, `WithVersion()` (a
`grpc.DialOption`) and `VersionClientInterceptor()`. Servers that need to
enforce a minimum version read the `x-swarmcracker-version` metadata directly
from the incoming context.

### Version History

| Version | Release | Changes |
|---------|---------|---------|
| `1` | v0.8.0+ | Initial schema — all v0.x releases share this version |
| (empty) | pre-v0.8.0 | Pre-versioning clients — treated as compatible |

## Health Check API

The daemon exposes a **local HTTP health endpoint** for monitoring:

| Attribute | Value |
|-----------|-------|
| **Bind address** | `127.0.0.1:8080` |
| **Endpoint** | `GET /healthz` |

The handler returns HTTP `200` when every check passes and HTTP `503`
otherwise.

### Response

```json
{
    "healthy": true,
    "checks": {
        "kvm": { "status": "ok", "message": "KVM is accessible" },
        "bridge": { "status": "ok", "message": "bridge swarm-br0 exists" },
        "firecracker": { "status": "ok", "message": "firecracker found at /usr/local/bin/firecracker" }
    }
}
```

Each check's `status` is `"ok"` or `"error"`; `message` carries the
human-readable detail. There are no `timestamp` or `consul` fields.

### Per-task health

The same server exposes the live healthcheck state of every task the node hosts,
which `service ps` / `task ls` fan out to:

| Attribute | Value |
|-----------|-------|
| **Endpoint** | `GET /v1/tasks/health` |
| **Method** | `GET` only (others get HTTP `405`) |

```json
{
    "tasks": [
        {
            "task_id": "5f3a1b2c9d0e",
            "state": "failing",
            "failing_streak": 2,
            "command": "/bin/sh -c curl -fsS http://localhost:8080/healthz",
            "output": "curl: (7) Failed to connect to localhost port 8080",
            "updated_at": "2026-10-16T15:04:07Z"
        }
    ]
}
```

`state` is one of `starting`, `healthy`, `failing` or `unhealthy` (see
[Container Healthchecks](/guides/operations/#seeing-health)). Tasks that declare
no healthcheck are absent. The response is deterministic (sorted by `task_id`).

**Trust model.** Health only — no authentication; the payload is the healthcheck
state plus the probe's last bounded output, which can carry whatever the check
printed. The bind address (`--health-addr`, default `127.0.0.1:8080`) is the
boundary; binding it on the cluster network exposes the same information as
`/healthz` and `/metrics`.

## Public HTTP API (v1)

Phase 1 ships a **read-only** HTTP API. The manager that initialized the cluster
serves the same v1 resource documents the CLI emits — `schemaVersion`, `kind`,
`items`, `next` for lists and `schemaVersion`, `kind` plus the resource fields for
single documents — on two listeners:

| Listener | Address | Authentication |
|----------|---------|----------------|
| **TLS/TCP** | `127.0.0.1:4244` by default (`--api-listen`) | `Authorization: Bearer <token>` on **every** route, including `/v1/version` |
| **Unix socket** | `<state-dir>/api.sock` (default `/var/lib/swarmkit/api.sock`) | none — the socket's file mode is the credential |

`api/openapi.yaml` in the repository is the normative contract for every route,
schema, header and error code; this section is the operator's guide to it.

Only the manager that initialized the cluster serves the API in phase 1: the
daemon starts both listeners when its configuration carries no join address
(`JoinAddr == ""`). A worker, and a manager that joined an existing cluster,
starts neither. Serving the API on joined managers is a follow-up. `--api-disabled`
turns both listeners off on the initializing manager, and `--api-listen ""` keeps
the Unix socket while disabling the TCP listener.

### Routes

Everything is `GET`. Phase 1 has no write routes.

| Route | Returns |
|-------|---------|
| `/v1/version` | `VersionInfo` (API versions, server version, capabilities) |
| `/v1/services` | `ServiceList` |
| `/v1/services/{id}` | `ServiceDocument` |
| `/v1/services/{id}/tasks` | `TaskList` |
| `/v1/tasks` | `TaskList` |
| `/v1/tasks/{id}` | `TaskDocument` |
| `/v1/nodes` | `NodeList` |
| `/v1/nodes/{id}` | `NodeDocument` |
| `/v1/networks` | `NetworkList` |
| `/v1/networks/{id}` | `NetworkDocument` |
| `/v1/configs` | `ConfigList` |
| `/v1/configs/{id}` | `ConfigDocument` |
| `/v1/secrets` | `SecretList` (metadata only — never a payload) |
| `/v1/secrets/{id}` | `SecretDocument` (metadata only) |

Lists accept `limit` and `cursor`; services, nodes, networks, configs and secrets
also accept `label`. Every response carries `X-SwarmCracker-Api-Version: 1` and
`X-Request-Id`, and every `200` carries an `ETag` (send it back as
`If-None-Match` to get `304`). Responses use the
`application/vnd.swarmcracker.v1+json` media type.

### Manager flags

| Flag | Default | Description |
|------|---------|-------------|
| `--api-listen` | `127.0.0.1:4244` | TLS listen address; empty disables the TCP listener |
| `--api-socket` | `<state-dir>/api.sock` | trusted Unix socket |
| `--api-cert-dir` | `<state-dir>/api` | directory holding `tls.crt` and `tls.key` |
| `--api-token-file` | `<state-dir>/api/tokens.json` | bearer token store |
| `--api-disabled` | `false` | do not start the API on this manager |

These flags belong to `swarmd-firecracker`. Defaults follow `--state-dir`, so
moving the state directory moves the socket, certificate and token store with it.

### TLS

TCP always verifies TLS, and there is deliberately no unverified mode. On first
start the manager generates a **self-signed certificate** for its hostname,
`127.0.0.1`, `::1` and the host part of `--api-listen`, and writes it to
`<api-cert-dir>/tls.crt` / `tls.key`.

Because the bootstrap certificate is self-signed, a remote client must trust it
explicitly with `--ca <api-cert-dir>/tls.crt`. The client uses no system trust
store and treats a missing `--ca` as a usage error rather than skipping
verification. If the certificate does not name the address you dial, pass
`--tls-server-name`. Signing the API certificate with the cluster CA is a
follow-up, not part of phase 1 — rotate the bootstrap certificate by replacing
the files in `--api-cert-dir` and restarting the daemon.

The Unix socket is **trusted**: it performs no token check, because the socket's
file mode (`0600`, owned by the daemon user) is the credential. Reach it with
`ssh` or a local `swarmcracker` invocation, not through a TCP proxy.

### Tokens

```bash
# On the manager: print a new secret once, then hand it to the client.
swarmcracker api token create --name ci --role reader

# Inspect or revoke the store (local file; never contacts a manager).
swarmcracker api token list
swarmcracker api token revoke <token-id>
```

`--role` is `reader` or `admin`. No phase-1 route distinguishes them: today
`admin` has exactly the same read access as `reader` and exists only as the
reserved role for the write surface a later phase adds. The secret is printed
once at creation and only its SHA-256 hash is written to `tokens.json`, so it
cannot be recovered later. The CLI's `--token-file` names that store; without it
the CLI uses `<SWARM_STATE_DIR or /var/lib/swarmkit>/api/tokens.json`. The daemon
re-reads the file when it changes, so a token minted or revoked while the daemon
runs takes effect without a restart.

### Remote CLI reads

A remote read is available on the contract path — `-o json` or `-o name` — for
`service ls|inspect|ps`, `task ls|inspect`, `node ls|inspect`,
`config ls|inspect`, `secret ls|inspect` and `network ls|inspect`. `service ls`
is the one command whose default table also reads the API, so `service ls`,
`service ls -o table` and `-o json` / `-o name` all work against `--host`.

Every other default table output for these commands is a **usage error** when
`--host` is set (`--host selects a remote manager: this command only supports the
local control socket; use a read command with -o json or -o name`), and any
command outside the list above is refused the same way. It never silently falls
back to the local cluster. Without `--host` the same commands read the local
socket, so a cluster member needs no flags.

```bash
swarmcracker -H https://mgr:4244 --ca <state-dir>/api/tls.crt \
  --token-file reader.token service ls
swarmcracker -H https://mgr:4244 --ca <state-dir>/api/tls.crt \
  --token-file reader.token service ls -o json
```

`reader.token` holds the raw secret (surrounding whitespace is trimmed).
`-o json` prints a v1 document, but for lists it is **not** a byte-for-byte
passthrough: the CLI follows every `next` cursor and rebuilds one document from
the merged pages, so `next` is always `null` and any `warnings`/`partial` from the
individual responses are dropped. Single-resource reads (`inspect`) emit the one
document they fetched. `-o name` prints identifiers one per line. JSON output is
available on the reads listed above.

### Errors and exit codes

A failed request answers with the `ErrorDocument` envelope — `schemaVersion`,
`kind: Error` and `error {code, message, requestId, retryable, details}` — and
the same `requestId` appears in the `X-Request-Id` response header. Codes are
stable; messages are not. The authoritative list of wire codes is the `Error`
schema in `api/openapi.yaml`. The CLI maps its stable codes to process exit
statuses in `pkg/output` (`usage`/`invalid`/`unsupported_version` → `2`,
`not_found`/`ambiguous` → `3`, `conflict` → `4`, `unauthenticated`/`forbidden` →
`5`, `rate_limited`/`unavailable`/`timeout`/`unreachable` → `6`, `partial` →
`7`, anything else → `1`).
